# OPS Dev Agent для Windows 11

Отдельный Telegram-контроллер разработки OPS Bot. Агент работает своим процессом,
использует `BBOT_TOKEN` и не зависит от перезапуска основного бота.

## Архитектура и файлы

Поток работы: Telegram → Controller → SQLite-очередь → App Server → реальные
файлы проекта → проверки → подтверждённый Git/deploy → Supervisor → Telegram.

Созданы:

- `dev_agent/__init__.py`, `dev_agent/main.py` — отдельная точка входа.
- `dev_agent/config.py`, `dev_agent/config.env.example` — настройки и шаблон.
- `dev_agent/telegram_controller.py` — команды, кнопки, авторизация и ответы.
- `dev_agent/codex_bridge.py` — stdio JSON-RPC App Server.
- `dev_agent/session_manager.py`, `dev_agent/task_manager.py` — сессии и очередь.
- `dev_agent/storage.py` — задачи, подтверждения, результаты и состояние в SQLite.
- `dev_agent/git_manager.py`, `dev_agent/test_runner.py` — Git и проверки.
- `dev_agent/supervisor.py`, `dev_agent/deploy_manager.py` — процессы и версии.
- `dev_agent/security.py`, `dev_agent/process.py`, `dev_agent/locking.py` —
  маскирование, контролируемые дочерние процессы и блокировки.
- `requirements-dev-agent.txt`, `start_dev_agent.bat` — установка и запуск.
- `tests/test_dev_agent.py` — автоматические проверки агента.
- `DEV_AGENT.md` — эта инструкция.

Изменены `main.py` (блокировка экземпляра OPS Bot) и `bot/bot.py` (локальный
запрос штатной остановки). Существующие `.env`, `.gitignore` и пользовательские
изменения `.env.example` сохранены.

## Первоначальная настройка

В PowerShell из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev-agent.txt
```

Добавьте в существующий `.env`:

```dotenv
BBOT_TOKEN=<токен отдельного бота управления>
DEV_AGENT_ADMIN_IDS=<ваш числовой Telegram ID>
```

Несколько ID перечисляются через запятую. Пустой список запрещает запуск.
Рабочий `TELEGRAM_BOT_TOKEN` остаётся отдельным. Опциональные параметры:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DEV_AGENT_CODEX` | `codex` | Путь к исполняемому Codex CLI |
| `DEV_AGENT_PYTHON` | Python, запустивший агент | Интерпретатор OPS Bot и проверок |
| `DEV_AGENT_TIMEOUT` | `1800` | Общий лимит одного хода Codex в секундах |
| `DEV_AGENT_RETENTION_DAYS` | `7` | Срок хранения содержимого завершённых задач |

Пустой `DEV_AGENT_PYTHON` не добавляйте: при необходимости укажите полный путь
к `.venv\Scripts\python.exe`. Шаблон: `dev_agent/config.env.example`.

Codex использует отдельный `CODEX_HOME`: `data/dev_agent/codex`. При первом
обращении копируется только локальный `auth.json` из обычного Codex, если он
существует. Конфигурация, инструкции и история VS Code не копируются. Если
авторизация хранится в системном хранилище или истекла, выполните вход отдельно:

```powershell
$env:CODEX_HOME = Join-Path (Get-Location) 'data\dev_agent\codex'
codex login
Remove-Item Env:CODEX_HOME
```

Авторизация через ChatGPT поддерживается самим CLI; API-ключ для агента не нужен.
После обновления CLI проверяйте совместимость протокола. Реализация проверялась
по JSON Schema установленного `codex-cli 0.169.0`.

Локальная проверка без Telegram-запросов:

```powershell
.\start_dev_agent.bat --check
```

Она проверяет конфигурацию, CLI, SQLite и состояние входа отдельного Codex.
Она не запускает модель, не отправляет сообщения и не запускает OPS Bot.

## Запуск

Только Dev Agent:

```powershell
.\start_dev_agent.bat
```

Dev Agent и OPS Bot под супервизором:

```powershell
.\start_dev_agent.bat --start-ops
```

Второй вариант требует чистого Git-дерева и сохранённого в коммите кода агента.
Сначала сохраните свои исходные изменения и эту реализацию обычным коммитом.
При первом запуске создаётся отдельная версия текущего коммита. Это исходная
точка восстановления для следующего деплоя. Самостоятельно коммит или push при
установке не выполняются.

Перед передачей управления остановите ручной OPS Bot в VS Code. Агент не убивает
чужие процессы. Общая блокировка в `main.py` запрещает две новые копии с одним
файлом блокировки; дополнительно проверяются процессы `main.py` в корне проекта.
Старые копии, запущенные до установки блокировки, нужно остановить вручную.
Копии из другого клона или на другом компьютере автоматически не обнаруживаются.

Ctrl+C завершает агент, активную задачу и управляемый OPS Bot. Сбой OPS Bot не
завершает агент. При аварийном выходе агента состояние PID и время создания
позволяют распознать оставшийся управляемый процесс после следующего запуска.

## Работа с телефона

В личном чате бота управления выполните `/start`. Группы и пользователи вне
allowlist игнорируются. Telegram username не используется для авторизации.

| Команда | Действие |
|---|---|
| `/start`, `/help` | Меню и справка |
| `/task описание` | Новая задача |
| `/tasks` | Последние задачи и их состояния |
| `/cancel [номер]` | Отмена активной или ожидающей задачи |
| `/status` | Агент, активная задача Codex, Git и OPS Bot |
| `/diff` | Diff отслеживаемых файлов относительно HEAD с маскированием секретов |
| `/git` | Список изменений и статистика |
| `/tests` | Синтаксис Python, Ruff, полный pytest |
| `/pull` | Подтверждённые fetch и fast-forward обновление чистой ветки |
| `/push` | Обзор, подтверждение, коммит изменений и обычный push |
| `/restart` | Подтверждённый перезапуск управляемой версии OPS Bot |
| `/start_ops` | Запустить OPS Bot (также кнопка «Запустить OPS Bot») |
| `/stop_ops` | Остановить OPS Bot (также кнопка «Остановить OPS Bot») |
| `/deploy` | Полные проверки, подтверждение, запуск новой версии |
| `/logs` | Последний диагностический вывод OPS Bot с маскированием |
| `/rollback` | Подтверждённый запуск предыдущей версии |

После завершения хода обычный текст продолжает последнюю сессию этого
пользователя с тем же номером задачи. Для отдельной задачи используйте `/task`.
Без сессии случайный текст не запускает Codex. Если Codex задал вопрос, ответьте
обычным сообщением. Несколько структурированных вопросов задаются последовательно.
Уточнение во время обычного выполнения нужно отправить после завершения хода;
параллельное изменение рабочего дерева запрещено.

Codex запускается в реальном рабочем дереве. Новая задача требует чистого Git.
Продолжение допускает изменения предыдущего хода, если их отпечаток не изменился.
Внешнее изменение файлов останавливает продолжение, чтобы сохранить вашу работу.
После сбоя с незакоммиченными изменениями сначала проверьте `/diff` и сохраните их.

Команды, задачи и деплой используют общую блокировку операций. `/status`, `/tasks`
и отмена доступны во время работы. Git, тесты и деплой в занятое дерево отклоняются;
самостоятельные задачи Codex выполняются последовательно из SQLite-очереди.

## Подтверждения и Git

Pull, push, restart, deploy и rollback требуют одноразовой кнопки, привязанной
к Telegram ID. Кнопка действует 5 минут. Изменение HEAD, ветки, origin, списка
файлов или содержимого файлов делает подготовленную операцию недействительной.
Повторная доставка Telegram update и повторное нажатие не повторяют операцию.
После перезапуска агента все старые подтверждения недействительны.

Push разрешён только для `Bakhytzhann/ops_bot` через HTTPS или SSH. Коммит
создаётся из текущих изменений; сообщение содержит имена изменённых файлов.
Перед push проверяется возможность обычного обновления ветки и исходящая история.
Force push, reset, clean, автоматический stash и перезапись ветки не используются.
Отказ Git или ошибка авторизации передаются владельцу. Созданный перед неудачным
push коммит остаётся локально.

`.gitignore` уже исключает `.env`, локальные базы, логи, ключи и `data/`.
Проверка публикации дополнительно блокирует чувствительные имена файлов,
известные из `.env` секреты, Telegram-токены, OpenAI-ключи и приватные ключи.
Произвольный неизвестный секрет невозможно надёжно распознать по содержимому:
проверяйте обзор изменений перед публикацией. Не отправляйте секреты в задачи.

## Деплой, проверка запуска и откат

Деплой требует чистого дерева. Сначала сохраните изменения коммитом, например
через подтверждённый `/push`. Проверки идут до запроса подтверждения. После
подтверждения повторно проверяется отпечаток файлов.

Версии создаются через detached Git worktree в
`data/dev_agent/releases/<commit>`. OPS запускается выбранным Python из этой
версии, а данные и логи остаются в основном проекте. Исходный `.env` загружается
в окружение процесса без копирования в каталог версии. Файлы текущей разработки
и код запущенного агента при откате не меняются.

Супервизор проверяет PID, время создания и полный путь `main.py`. Для штатной
остановки создаёт индивидуальный локальный stop-файл; бот завершает polling через
`Application.stop_running()`. После ожидания допускается принудительное завершение
только проверенного процесса и его дочерних процессов. Нельзя запускать операции
управления против неизвестного PID.

После запуска проверяются существование процесса, `PRAGMA quick_check` базы и
критические ошибки нового stdout/stderr. Результат обозначается как **частично
подтверждённый запуск**: это не доказывает готовность Telegram polling и внешних
интеграций. Проверьте обычную работу OPS Bot вручную. Внутреннее поле
`verified_release` означает версию, прошедшую эти локальные проверки.

При неудачном запуске новой версии агент пытается запустить предыдущую.
`/rollback` также переключает каталог запуска, а не откатывает Git рабочего дерева.
До первого сохранённого запуска предыдущей версии может не быть. Базы данных
при откате кода не откатываются: несовместимые миграции требуют отдельного плана
резервного копирования. Каталоги версий автоматически не удаляются.

При неожиданном завершении OPS Bot предусмотрены максимум три восстановления
за время работы агента, с увеличивающейся задержкой. Затем нужен ручной разбор.
При перезапуске агента прерванные задачи получают `failed`; ожидающие сохраняются.
Состояние незавершённого деплоя видно в SQLite, автоматическая повторная публикация
или повторный деплой после перезапуска не выполняются.

## Границы разрешений и хранения

App Server использует `workspace-write`, ограниченную сеть и `on-request`.
Запросы разрешения на команды и изменения файлов передаются владельцу; неизвестные
виды запросов отклоняются. Разрешение выдаётся на один запрос, без постоянного
ослабления политики. Текст Telegram никогда напрямую не передаётся shell.

Рабочая sandbox Codex ограничивает запись, но не является гарантией запрета
чтения `.env` или любых файлов пользователя. Инструкции модели запрещают чтение
секретов и изменение управляющего кода, однако сами по себе не обеспечивают
изоляцию от злонамеренной модели. Для строгого запрета чтения требуется отдельная
учётная запись Windows и ACL на секреты, либо внешняя изоляция. Не подтверждайте
команду, выходящую за пределы задачи. Эта реализация не заявляет полной защиты
компьютера от одобренной владельцем опасной команды.

SQLite хранит минимальную историю задач, результаты проверок, подтверждения и
операции. Содержимое завершённых задач и ссылки на их сессии очищаются при запуске
по сроку хранения. Старые JSONL-файлы удаляются только в собственном каталоге
сессий агента. `auth.json` не удаляется. Обычные сессии VS Code не затрагиваются.
Это не означает удаления серверных копий данных OpenAI. Автоматическая ротация
диагностических логов ограничивает их размер, но срок ротации определяется объёмом.

Логи агента: `logs/dev_agent.log`; OPS stdout/stderr: `logs/dev_agent_ops.log`.
Секреты маскируются перед записью и отправкой. Исходные логи самого OPS Bot
продолжают подчиняться его собственной настройке логирования.

## Автозапуск через Task Scheduler

Настройте вручную после проверки интерактивного запуска:

1. Создайте задачу `OPS Dev Agent` для своей учётной записи, без повышенных прав.
2. Триггер — вход пользователя в Windows.
3. Программа — полный путь к `.venv\Scripts\pythonw.exe`.
4. Аргументы — `-m dev_agent.main --start-ops` или `-m dev_agent.main`.
5. Рабочий каталог — полный путь к `ops_bot`.
6. Запретите запуск второго экземпляра задачи. Уберите ограничение времени работы.
7. Убедитесь, что Codex доступен в PATH этой учётной записи, либо задайте его
   полный путь через `DEV_AGENT_CODEX`.

Установщик не создаёт и не изменяет задачи Windows. Принудительное завершение
через Task Scheduler может оставить дочерний процесс; следующий запуск проверит
его сохранённую идентичность, а блокировка OPS не позволит запустить дубликат.

## Проверки разработки

```powershell
$env:DEBUG = 'false'
.\.venv\Scripts\python.exe -m compileall -q dev_agent main.py bot/bot.py
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m pytest -q
```

`DEBUG=false` исключает конфликт с унаследованным системным `DEBUG=release`.
Тесты агента используют временные каталоги, mock Telegram, mock Codex и mock
супервизор. Локальные проверки Git работают только во временном репозитории.
Реальных push, сообщений Telegram и перезапусков рабочего OPS Bot из тестов нет.
Проверка протокола использует схему CLI, если она сгенерирована в
`data/dev_agent_schema`; без неё один дополнительный тест пропускается.

Первую реальную проверку Telegram → Codex → тесты → deploy выполняйте отдельно
после настройки allowlist и сохранения исходного коммита. Она не выполнялась
при первоначальной разработке, согласно ограничениям задания.
